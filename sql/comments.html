SQL Comments

10 Min Read • Module 1: Basics

The Architectural Blueprint Sticky Note Analogy

Picture a structural civil engineer reviewing the blueprint schematics for a modern commercial facility:

1. The Formal Construction Blueprint: Structural walls, steel columns, load-bearing headers, and electrical conduits represent executable structural directives obeyed by the construction team.

2. The Architect's Annotation: The lead architect affixes a yellow sticky note: 'Reinforced carbon rebar required here due to high seismic foundation stresses.'

3. Completely Invisible to Building Concrete: The sticky note does not add physical steel or weight to the physical foundation; the concrete pouring machinery ignores it completely.

4. Invaluable Future Clarity: The annotation prevents disastrous mistakes and saves future renovation teams weeks of reverse-engineering during building expansions.

SQL comments document query intent, mathematical formulas, and business constraints for human developers, ignored entirely by the database query execution engine.

Syntax & Statement Grammar

The standard SQL syntax and pattern rules for SQL Comments:

SQL Syntax Grammar Blueprint 
-- 1. Single-Line Comment (Ignored until end of line)
SELECT column_name -- In-line field documentation
FROM table_name;

/* 
   2. Multi-Line Block Comment
   Spans across multiple lines
   Ideal for script headers and complex business rules
*/
SELECT * FROM table_name;

SQL Comments Blueprint Breakdown

Core rules and architectural mechanics governing code documentation and query debugging in relational engines:

  • Single-Line Comments (--): Any text starting with two consecutive dashes is ignored by the database lexer until the newline character.
  • Multi-Line Block Comments (/* ... */): Text enclosed between /* and */ is treated as whitespace, enabling documentation across many lines or inline inside expressions.
  • Zero Query Plan Overhead: Comments are stripped during lexical tokenization; they have zero negative impact on query execution plans or execution speeds.
  • Debugging and Isolation: Developers frequently use block comments to temporarily comment out WHERE clauses or join conditions without deleting working code.

Interactive Query Terminals

Explore production-grade implementations of single-line and multi-line SQL comments running against active relational tables (employees, transactions, accounts, and branches):

Query 1: Single-Line Merit Increase Documentation 
-- Calculate projected annual merit increase based on department performance
SELECT 
    employee_id,
    first_name,
    last_name,
    department,
    salary,
    ROUND(salary * 1.08, 2) AS projected_salary -- Standard 8% annual merit increase
FROM employees
WHERE department = 'Engineering';

Single-Line Annotation Breakdown

Auditing the execution logic and relational mechanics of this query:

  • Uses A: Uses a leading -- comment to state the overarching objective of the query for finance auditors.
  • Uses An: Uses an inline comment after projected_salary explaining the exact 1.08 multiplier formula.
  • Executes Seamlessly: Executes seamlessly against employees, returning 4 Engineering personnel with calculated projections.

Query 2: Multi-Line Script Header Documentation 
/*
=====================================================
Pipeline: Executive Daily Settlement Reconciliation
Author: Treasury Operations & Risk Analytics
Purpose: Aggregates settled transaction volume
         grouped by status while auditing exposure.
=====================================================
*/
SELECT 
    status,
    COUNT(*) AS total_transactions,
    ROUND(SUM(amount), 2) AS aggregate_volume
FROM transactions
GROUP BY status;

Auditing the execution logic and relational mechanics of this query:

  • Encloses A: Encloses a full production header inside /* ... */ block comment syntax.
  • Documents Pipeline: Documents author identity, pipeline name, and operational scope directly within the SQL file.
  • Aggregates transactions: Aggregates transactions into settlement categories, totaling $276,400.00 across 167 completed records.

Query 4: Annotated Relational Join Pipeline 
-- Extract client portfolio and deposit metrics
SELECT 
    c.customer_id,
    c.first_name,
    c.last_name,
    COUNT(a.account_id) AS total_accounts, -- Total open and active accounts
    ROUND(COALESCE(SUM(a.balance), 0), 2) AS total_deposited_balance
FROM customers c
INNER JOIN accounts a ON c.customer_id = a.customer_id
WHERE c.customer_id <= 20 -- Sampling first cohort
GROUP BY c.customer_id, c.first_name, c.last_name
ORDER BY total_deposited_balance DESC;

Annotated Join Pipeline Breakdown

Auditing the execution logic and relational mechanics of this query:

  • Combines Multiple: Combines multiple single-line comments across projections, joins, and filtering conditions.
  • Explains mathematical aggregations (COUNT, COALESCE, and SUM) to prevent misinterpretation.
  • Returns Active: Returns active cohort accounts sorted by highest total deposited balance.

Core Concepts & Engine Mechanics

Commenting standards differ between development environments and automated database deployment tools.

Comment Type Syntax Pattern Span Scope Primary Use Case Performance Impact
Single-Line -- text Until line break Inline notes, field definitions None (Zero runtime cost)
Multi-Line Block /* text */ Across multiple lines File headers, logic documentation None (Zero runtime cost)
Inline Block /* text */ Within single line Commenting out operators / clauses None (Zero runtime cost)
Optimizer Hint /*+ HINT */ Inside query block Directing index selection / join order Alters physical execution plan

Production Commenting Hygiene & Security

Follow these professional guidelines when writing SQL comments in enterprise software teams:

  • Never Store Secrets: Never include passwords, API keys, private customer PII, or internal server IP addresses in SQL comments.
  • Keep Comments in Sync with Code: Outdated comments that contradict actual SQL logic are more dangerous than no comments at all. Update comments whenever query logic changes.
  • Explain the "Why", Not the "What": Avoid obvious statements like -- SELECT FROM CUSTOMERS. Instead, explain non-obvious business rules like -- Exclude churned trial accounts per Q4 finance directive.

Real-World Practical Scenario

Executive Branch Liquidity Audit: Examine how comprehensive documentation improves the readability of deposit aggregation reports across active branch operations.

Production Query: Documented Branch Liquidity Report 
/* 
   Executive Audit: High-Volume Branch Liquidity Breakdown
   Filters active checking and savings portfolios to compute reserve impact
*/
SELECT 
    b.branch_name,
    COUNT(a.account_id) AS active_accounts,
    ROUND(AVG(a.balance), 2) AS avg_account_balance,
    ROUND(SUM(a.balance), 2) AS total_branch_deposits
FROM accounts a
INNER JOIN branches b ON a.branch_id = b.branch_id
WHERE a.status = 'Active' -- Strict active reserve filter
GROUP BY b.branch_name
ORDER BY total_branch_deposits DESC;

Documented Branch Liquidity Report Breakdown

Auditing the execution logic and relational mechanics of this query:

  • Combines High-Level: Combines high-level multi-line documentation with focused inline filter notes.
  • Demonstrates How: Demonstrates how clear annotations enable engineers to immediately recognize that only active accounts are evaluated.
  • Summarizes branch liquidity reserves led by premier metropolitan branch hubs.

Best Practices & Production Guidelines

  • Header Standards: Include script name, author, creation date, and Jira/ticket tracking numbers at the top of complex stored procedures and migration scripts.
  • Sanitize Migration Logs: Some database migration tools strip comments during execution; verify whether your deployment pipeline preserves SQL docstrings.

Chapter Summary

SQL comments provide human-readable documentation that clarifies business logic and assists query debugging with zero performance penalty.

  • Single-Line (--): Annotate inline formulas and specific filter conditions.
  • Multi-Line (/* */): Document procedural headers, data pipelines, and architectural assumptions.
