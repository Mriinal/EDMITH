ACID Properties & Transaction Architecture

20 Min Read • Module 3: References

The Bank ATM & Ledger Transfer Analogy

Imagine transferring $500 from your checking account to your savings account via a mobile banking app. Behind the scenes, the database must execute two separate updates: debit $500 from Checking, and credit $500 into Savings. The ACID guarantees ensure your money never vanishes:

  • A - Atomicity ("All or Nothing"): Either both the deduction and the addition succeed together, or the entire operation rolls back to zero as if it never happened. If the server loses power after step 1, your $500 is never lost in limbo.
  • C - Consistency ("Rules & Invariants Maintained"): The database guarantees that all integrity constraints (balances cannot go negative, total dollars across the bank remain identical) are preserved before and after the transfer.
  • I - Isolation ("Invisible Concurrency"): If your spouse tries to withdraw money from the same account at the exact millisecond your transfer is running, the database prevents dirty reads and race conditions by isolating the transactions.
  • D - Durability ("Surviving Disasters"): Once the app displays "Transfer Successful", that record is permanently flushed to non-volatile disk logs (WAL). Even if lightning strikes the datacenter 5 milliseconds later, your $500 is safely in Savings.

ACID properties form the cornerstone of Relational Database Management Systems (RDBMS), separating enterprise transactional engines from raw file stores.

Core Concepts & Engine Mechanics

The acronym ACID was coined in 1983 by computer scientist Andreas Reuter and Jim Gray. It establishes the four essential requirements that guarantee database transactions are processed reliably, even in the presence of power outages, hardware failures, concurrent users, and system crashes.

A • Atomicity

"All or Nothing Execution"

A transaction is treated as a single, indivisible unit of work. If any statement fails (due to syntax errors, constraint violations, or server crash), the database rolls back all preceding statements using the Undo Log.

  • Undo Logs track reverse operations
  • Prevents partial state writes
  • Controlled via COMMIT & ROLLBACK

C • Consistency

"Preserving Schema Rules"

Transactions can only transition the database from one valid state to another valid state. All schema constraints (PRIMARY KEY, FOREIGN KEY, CHECK, UNIQUE, NOT NULL) and triggers must be satisfied.

  • Enforces database invariants
  • Cascading integrity checks
  • Guarantees zero corrupted references

I • Isolation

"Concurrency Independence"

Multiple concurrent transactions execute without interfering with one another. Intermediate, uncommitted changes made by one transaction are invisible to other sessions depending on the Isolation Level.

  • MVCC (Multi-Version Concurrency)
  • Shared vs Exclusive Lock escalation
  • Prevents dirty reads and race conditions

D • Durability

"Permanent Disaster Survival"

Once a transaction commits, its modifications are permanently recorded on non-volatile media. Even in the event of an abrupt power shutdown, kernel panic, or OS crash, committed updates are never lost.

  • Write-Ahead Logging (WAL / Redo Log)
  • Periodic disk checkpointing (fsync)
  • Automated crash recovery on reboot

The 4 ANSI SQL Transaction Isolation Levels

Isolation involves an engineering trade-off: higher isolation guarantees absolute correctness but decreases concurrent throughput by holding locks or managing multi-version rows. ANSI SQL defines four distinct isolation levels:

Isolation Level Dirty Reads Non-Repeatable Reads Phantom Reads Concurrency / Performance Common Usage
READ UNCOMMITTED Allowed Allowed Allowed Maximum Throughput (Zero Read Locks) Rough analytics, telemetry estimations
READ COMMITTED Prevented Allowed Allowed High Throughput (Default in PG, Oracle, SQL Server) Standard web apps, CRUD APIs
REPEATABLE READ Prevented Prevented Allowed (PG MVCC prevents) Moderate (Default in MySQL InnoDB) Financial reporting, batch rollups
SERIALIZABLE Prevented Prevented Prevented Lowest Throughput (Strict Ordering / SSI) Banking ledgers, cryptographic trades

Understanding Concurrency Anomalies

  • Dirty Read (Uncommitted Dependency): Transaction A updates a row but has not committed yet. Transaction B reads the modified row. Transaction A then encounters an error and rolls back. Transaction B now possesses data that never officially existed!
  • Non-Repeatable Read (Fuzzy Read): Transaction A reads a row. Transaction B updates or deletes that same row and commits. Transaction A re-reads the row and observes altered column values within the same session.
  • Phantom Read: Transaction A queries a range of rows (e.g., WHERE salary > 100000). Transaction B inserts a brand-new employee with a $120,000 salary and commits. When Transaction A runs the identical range query again, a new "phantom" row appears in the result set.

Common Mistakes & Anti-Patterns

  • Long-Running Transactions: Holding transactions open while performing external API network calls or waiting for user inputs holds locks indefinitely, causing connection pool starvation and database-wide deadlocks.
  • Missing Transaction Boundaries in Batch Processing: Inserting 100,000 rows in individual single-row auto-commit transactions triggers 100,000 separate disk fsync calls. Always batch writes inside an explicit transaction block.
  • Confusing ACID Consistency with CAP Theorem Consistency: "C" in ACID means preserving local schema rules and invariants (FK, PK, Check). "C" in the CAP theorem refers to Linearizability (every read in a distributed cluster returns the latest write).
  • Overusing SERIALIZABLE: Blindly setting isolation to Serializable causes excessive transaction aborts and serialization failures under high concurrency. Rely on Read Committed with optimistic locking or row versioning where appropriate.

Senior Engineering Interview Questions & Answers

Q1: How does Multi-Version Concurrency Control (MVCC) achieve high concurrency?

In traditional locking engines, readers block writers and writers block readers. MVCC solves this by maintaining multiple historical versions of each modified row (often tagged with transaction IDs: xmin/xmax in PostgreSQL or undo logs in MySQL). When a reader queries the database, it views a snapshot of data as it existed when the transaction started. Readers never block writers, and writers never block readers.

Q2: What is Write-Ahead Logging (WAL) and why is it essential for Durability?

Writing changes randomly across multiple data pages on disk is slow. Instead, Write-Ahead Logging dictates that before any table data page is modified on disk, a sequential description of the change must be safely appended to an append-only log file on non-volatile storage and flushed. If the server crashes, the database re-reads the WAL during reboot and replays committed changes (Redo phase), guaranteeing Durability with minimal disk I/O overhead.

Q3: What is a Write Skew anomaly and which isolation level prevents it?

Write skew occurs when two concurrent transactions read overlapping data, verify a shared business rule, but then write to disjoint rows such that the overall invariant is violated. For example, a hospital rule requires at least one on-call doctor. Two doctors simultaneously check the roster (seeing two doctors on duty) and both request leave, resulting in zero doctors on duty. Because neither doctor updated the other's row, REPEATABLE READ permits it. Only SERIALIZABLE isolation detects write skew and aborts one transaction.

Chapter Summary

ACID properties guarantee that database transactions execute predictably and safely, safeguarding enterprise data integrity across concurrent user interactions and catastrophic hardware crashes.

  • Atomicity (Undo Logs): Guarantees all-or-nothing execution. Partial transaction failures are completely reversed.
  • Consistency (Constraints): Enforces that all schema invariants, foreign keys, and business rules remain strictly valid before and after transactions.
  • Isolation (MVCC & Locks): Separates concurrent sessions across 4 ANSI isolation levels, balancing performance against dirty, fuzzy, and phantom reads.
  • Durability (WAL & fsync): Guarantees that committed modifications survive power failure through append-only write-ahead logs.
  • Transaction Control: Explicitly demarcate critical updates using BEGIN TRANSACTION, COMMIT, ROLLBACK, and SAVEPOINT.
