The Priority Rule (SQL Order of Execution)

20 Min Read • Non-Negotiable Core Rule

The Great SQL Paradox

When you write a sentence in English, you read it from left to right. When you write a SQL query, you naturally begin with the keyword SELECT. However, the database engine does not begin executing your query with SELECT!

SQL is a declarative language: you specify what data you want, not how to retrieve it. To optimize speed and minimize memory consumption, every SQL query engine follows a strict, hidden hierarchy called The Priority Rule (Logical Order of Query Execution).

Mastering this order is what separates junior coders from senior Data Engineers. It explains why certain queries throw bizarre errors like "Column alias not found" and unlocks your ability to write blazingly fast database queries.

The Factory Assembly Line Analogy

Imagine a factory producing custom customized juice packages:

1. FROM & JOIN: The warehouse trucks arrive with crates of raw fruit (Tables & Datasets).

2. WHERE: Workers discard any spoiled or rotten fruit before processing (Row filtering).

3. GROUP BY: The remaining fruit is organized into bins: Oranges, Apples, and Grapes (Aggregation grouping).

4. HAVING: Bins with fewer than 50 fruits are removed from the production line (Group filtering).

5. SELECT: The juice is extracted, measured, and branded with a custom label (Column projection & Aliases).

6. DISTINCT: Duplicate identical bottles are discarded.

7. ORDER BY: The bottles are neatly arranged from highest price to lowest on the display rack (Sorting).

8. LIMIT / OFFSET: Only the first 10 bottles are placed into the delivery basket (Pagination).

How You Write It vs How the Database Runs It

Notice how SELECT is written first, but executed near the very end:

Phase Syntactic Order (How You Write It) Logical Execution Order (The Priority Rule)
Step 1 SELECT (Written 1st) FROM & JOIN (Executes 1st)
Step 2 FROM (Written 2nd) WHERE (Executes 2nd)
Step 3 WHERE (Written 3rd) GROUP BY (Executes 3rd)
Step 4 GROUP BY (Written 4th) HAVING (Executes 4th)
Step 5 HAVING (Written 5th) SELECT (Executes 5th)
Step 6 ORDER BY (Written 6th) DISTINCT (Executes 6th)
Step 7 LIMIT / OFFSET (Written 7th) ORDER BY (Executes 7th)
Step 8 — LIMIT / OFFSET (Executes 8th)

Step-by-Step: The 8 Phases of Execution

1. FROM & JOIN (Locate the Data)

The database engine first identifies the source tables. If you are combining tables with INNER JOIN, LEFT JOIN, or CROSS JOIN, the engine merges them into a working Cartesian virtual table. Without source data, nothing else can proceed.

2. WHERE (Filter Raw Rows)

The engine applies your boolean predicates to filter individual rows. Any row that does not evaluate to TRUE is immediately discarded. This happens before any grouping or aggregate calculations take place, making it crucial for query performance.

3. GROUP BY (Aggregate into Buckets)

The rows surviving the WHERE filter are partitioned into unique group sets based on the columns listed in GROUP BY. From this point forward, the query no longer views single individual rows; it operates on entire summary groups.

4. HAVING (Filter Aggregated Buckets)

Once groups exist, HAVING filters out groups that do not meet aggregate conditions (such as COUNT(*) > 5 or AVG(salary) > 80000). Rows cannot be filtered with aggregate functions inside WHERE because groups haven't formed yet!

5. SELECT (Evaluate Expressions & Aliases)

Only now does the engine evaluate the expressions inside the SELECT clause! It computes mathematical formulas, concatenates strings, formats columns, and assigns column aliases (e.g., AS total_amount).

6. DISTINCT (Deduplicate)

If you included the DISTINCT keyword, the engine examines the projected columns from Step 5 and eliminates any duplicate rows.

7. ORDER BY (Sort Final Rows)

The engine sorts the final dataset ascending (ASC) or descending (DESC). Because SELECT has already executed, you can sort by aliases created in the SELECT clause!

8. LIMIT / OFFSET (Slice Output)

Finally, the engine discards rows outside your pagination boundary. LIMIT 10 takes only the top 10 rows of the ordered result set.

Concrete Example: Tracing a Real Query

Let's trace how the database engine executes this multi-clause query on our customers dataset step-by-step:

The Priority Rule: Complete Multi-Clause Query Trace 
-- Goal: Find the most frequent first names among customers with ID <= 500
SELECT 
    first_name,
    COUNT(*) AS name_count
FROM customers
WHERE customer_id <= 500
GROUP BY first_name
HAVING COUNT(*) >= 5
ORDER BY name_count DESC
LIMIT 5;

Behind-the-Scenes Execution Trace

Even though the SELECT keyword appears first in your written code, the database engine executes this query according to the strict logical order of the Priority Rule:

  • 1. FROM (customers): The engine identifies and loads the source customers table (612 records) into working memory.
  • 2. WHERE (customer_id <= 500): Evaluates individual rows before any grouping occurs; all customer records with IDs greater than 500 are immediately excluded.
  • 3. GROUP BY (first_name): The remaining rows are partitioned into distinct buckets based on matching first_name values.
  • 4. HAVING (COUNT(*) >= 5): Filters the aggregated buckets, keeping only name groups that contain 5 or more customer records.
  • 5. SELECT (first_name, COUNT(*) AS name_count): The engine extracts the requested columns and computes the alias name_count for each qualified group.
  • 6. ORDER BY (name_count DESC): Sorts the surviving groups in descending order based on the calculated alias.
  • 7. LIMIT (5): Slices the final sorted result set to return exactly the top 5 most common customer names.

The 3 Classic Traps (And How to Avoid Them)

Trap 1: The "Unknown Column Alias" in WHERE

Beginners frequently attempt to filter rows by referring to a calculated alias defined in the SELECT clause:

Trap 1: Column Alias Visibility (WHERE vs SELECT) 
-- ❌ INCORRECT: In standard SQL engines, this throws "Column alias 'given_name' not found":
-- SELECT customer_id, first_name AS given_name FROM customers WHERE given_name = 'Mrinal';

-- ✅ CORRECT: Filter using the physical column name in WHERE
SELECT customer_id, first_name AS given_name
FROM customers
WHERE first_name = 'Mrinal';

Why Column Aliases Fail in WHERE

Understanding why this fails is the most practical benefit of learning the Priority Rule:

  • WHERE (Step 2) Precedes SELECT (Step 5): When the engine executes WHERE to filter rows, SELECT has not executed yet. The alias given_name does not exist anywhere in database memory at that point in time.
  • The Solution: Always refer to the original database column identifier (first_name) or repeat the raw calculation in the WHERE clause.

Trap 2: Aggregate Functions in WHERE

Another classic mistake is attempting to filter rows using aggregate functions like COUNT(), SUM(), or AVG() directly inside the WHERE clause:

Trap 2: Aggregates in WHERE vs HAVING 
-- ❌ INCORRECT: Throws "ERROR: An aggregate function may not appear in WHERE":
-- SELECT first_name, COUNT(*) AS total_count FROM customers WHERE COUNT(*) > 5 GROUP BY first_name;

-- ✅ CORRECT: Use HAVING to filter groups after GROUP BY
SELECT first_name, COUNT(*) AS total_count
FROM customers
GROUP BY first_name
HAVING COUNT(*) > 5;

WHERE Filters Rows, HAVING Filters Groups

The distinction between WHERE and HAVING is strictly governed by execution order:

  • Why Aggregates Fail in WHERE: WHERE executes in Step 2, evaluating individual rows one by one. Grouping has not taken place yet, so group totals like COUNT(*) are mathematically undefined at this stage.
  • Why HAVING Succeeds: GROUP BY (Step 3) aggregates rows into buckets. Immediately following, HAVING (Step 4) filters those formed buckets based on aggregate criteria.

Trap 3: Using Aliases in ORDER BY (Why it WORKS!)

New SQL learners often ask: "If column aliases fail in WHERE, why are they fully supported in ORDER BY?"

Trap 3: Why Aliases Work Seamlessly in ORDER BY 
-- ✅ Perfectly Valid SQL: Aliases are fully accessible in ORDER BY
SELECT first_name, COUNT(*) AS total_customers
FROM customers
GROUP BY first_name
ORDER BY total_customers DESC
LIMIT 5;

Why ORDER BY Recognizes SELECT Aliases

The answer once again lies in the chronological execution sequence:

  • SELECT (Step 5) Executes Before ORDER BY (Step 7): By the time the database engine sorts the resulting rows in ORDER BY, SELECT has already evaluated all expressions and assigned their aliases (e.g. total_customers).
  • Clean & Efficient: Referencing column aliases in ORDER BY avoids writing duplicate aggregate expressions and keeps query code clean and readable.

Chapter Summary

The Priority Rule dictates the non-negotiable logical order in which database engines execute SQL queries. Understanding that queries run in the sequence FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT is what empowers engineers to write bug-free queries and optimize data retrieval performance.

  • The Priority Sequence: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT.
  • WHERE vs HAVING: WHERE filters individual records before grouping; HAVING filters aggregated groups after GROUP BY.
  • Alias Visibility: Aliases created in SELECT are inaccessible to WHERE and HAVING, but are fully available to ORDER BY.
  • Performance Insight: High-selectivity filters in WHERE reduce the dataset early, drastically accelerating downstream GROUP BY and ORDER BY steps.
