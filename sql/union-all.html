The UNION ALL Operator

15 Min Read • Module 1: Basics

The Combined Warehouse Delivery Logs Analogy

Imagine managing logbooks across multiple distribution docks at an enterprise fulfillment center:

1. Loading Dock A: Logs every delivery van arrival: Van #101, Van #102, Van #103.

2. Loading Dock B: Logs regional transfer arrivals: Van #101, Van #104, Van #105.

3. The UNION ALL Merge: You stack both daily gate records directly into a master timeline. Van #101 appears twice, exactly capturing the physical reality that it entered both loading docks during the day!

4. Zero Deduplication Overhead: Stacking requires zero sorting, zero hashing, and zero wait time. Every single recorded event is faithfully preserved.

The UNION ALL set operator stacks results instantly without deduplication, preserving complete historical event frequency with maximum CPU and memory throughput.

Syntax & Statement Grammar

The standard SQL syntax and pattern rules for The UNION ALL Operator:

SQL Syntax Grammar Blueprint 
SELECT column1, column2, ... column_n
FROM table1
[WHERE condition1]
UNION ALL
SELECT column1, column2, ... column_n
FROM table2
[WHERE condition2]
[ORDER BY column1 [ASC | DESC]];

UNION ALL Blueprint Breakdown

Core rules and architectural mechanics governing set union-all streaming operations in relational engines:

  • Zero Deduplication Pass: Unlike regular UNION, UNION ALL does not perform sort or hash comparisons to eliminate duplicate tuples; every record from both sources is emitted immediately.
  • High-Throughput Streaming: Operates in constant memory O(1) per row by piping records directly to the consumer stream as they are fetched from storage.
  • Identical Cardinality: Each sub-statement must project the exact same number of columns in matching sequential order.
  • Type Concordance: Corresponding columns across all participating SELECT queries must possess compatible data types.
  • Global Ordering: A single terminal ORDER BY clause sorts the combined stream before final delivery.

Interactive Query Terminals

Explore production-grade implementations of UNION ALL running against active relational tables (sells_list, employees, product_list, and customers):

Query 1: Partitioned Channel Sales Concatenation 
SELECT sale_id, customer_id, product_id, total_price, 'ELECTRONICS' AS channel
FROM sells_list
WHERE product_id BETWEEN 1 AND 7
UNION ALL
SELECT sale_id, customer_id, product_id, total_price, 'HOME_OFFICE' AS channel
FROM sells_list
WHERE product_id BETWEEN 8 AND 15
ORDER BY total_price DESC;

Partitioned Channel Sales Concatenation Breakdown

Auditing the execution logic and relational mechanics of this query:

  • Combines Two: Combines two partitioned product subsets from sells_list into a single 38-row high-performance stream.
  • Because The: Because the product ID ranges are mutually disjoint (1-7 vs 8-15), duplicate rows cannot exist; using UNION ALL saves unnecessary CPU cycles.
  • Sorts the entire unified transaction stream from largest to smallest order value via ORDER BY total_price DESC.

Query 2: Dual Audit Batch Streaming (Duplicate Retention) 
SELECT department, 'STREAM_A' AS origin FROM employees WHERE employee_id <= 5
UNION ALL
SELECT department, 'STREAM_B' AS origin FROM employees WHERE employee_id <= 5;

Dual Audit Batch Streaming Breakdown

Auditing the execution logic and relational mechanics of this query:

  • Demonstrates the fundamental behavior of UNION ALL: all rows from both queries are preserved, resulting in exactly 10 rows (5 + 5).
  • In standard UNION, repeated department entries would be flattened into unique values; here, every occurrence remains intact.
  • Essential For: Essential for event logging, audit trails, and financial reconciliation where every transaction instance must be accounted for.

Query 3: Consolidated Enterprise Cash-Flow Ledger 
SELECT c.customer_id AS account_id, c.first_name || ' ' || c.last_name AS account_name, s.total_price AS volume, 'REVENUE' AS ledger_type
FROM sells_list s
JOIN customers c ON s.customer_id = c.customer_id
WHERE s.total_price >= 1000.00
UNION ALL
SELECT e.employee_id AS account_id, e.first_name || ' ' || e.last_name AS account_name, e.salary AS volume, 'PAYROLL_EXPENSE' AS ledger_type
FROM employees e
WHERE e.salary >= 100000.00
ORDER BY volume DESC;

Consolidated Enterprise Cash-Flow Ledger Breakdown

Auditing the execution logic and relational mechanics of this query:

  • Merges incoming customer sales revenue ($1000+) with outgoing executive salary liabilities ($100,000+) into a single cash-flow balance sheet.
  • Preserves exact monetary amounts even if a customer purchase amount matches an employee payroll figure.
  • Demonstrates Cross-Functional: Demonstrates cross-functional relational joins within individual UNION ALL branches.

Query 4: Holistic Multi-Source Cardinality Metric 
SELECT COUNT(*) AS total_stream_records
FROM (
    SELECT sale_id, total_price FROM sells_list
    UNION ALL
    SELECT product_id, price FROM product_list
) AS unified_event_stream;

Holistic Multi-Source Cardinality Metric Breakdown

Auditing the execution logic and relational mechanics of this query:

  • Pipes 60 rows from sells_list and 25 rows from product_list through a derived table subquery to compute the aggregate event volume (85 total records).
  • Because Union: Because UNION ALL preserves all rows without deduplication, the mathematical sum is exactly COUNT(table1) + COUNT(table2).
  • Allows Data: Allows data pipelines to verify total ingestion volume before loading into downstream analytics warehouses.

Core Concepts & Engine Mechanics

The UNION ALL operator is the fastest set operator available in relational databases. It bypasses the sorting buffer and hash indexing steps required by UNION, delivering raw streaming throughput.

Set Operation Duplicate Handling Algorithm Complexity Memory Allocation Optimal Use Case
UNION ALL Preserves all duplicate rows O(N) Streaming pass Minimal O(1) buffer High-volume ingestion, append-only logs, disjoint partitions
UNION Deduplicates all tuples O(N log N) Sort / Hash High (Buffers full dataset) Merging overlapping identity lists where duplicates violate logic
INTERSECT Retains rows common to both Hash / Sort Intersection Moderate Cohort overlap analysis and cross-platform user verification
EXCEPT / MINUS Subtracts query 2 from query 1 Hash Anti-Join Moderate Churn detection and delta synchronization between tables

The Senior Engineer's Performance Rule

In high-scale enterprise systems, experienced database engineers apply a simple default rule:

  • Default to UNION ALL: Unless business requirements explicitly mandate unique row deduplication, always write UNION ALL. It avoids creating memory bottlenecks on production database instances.
  • Partitioned Architecture: In time-partitioned tables (e.g., sales by month or year), rows across partitions are physically unique. Using plain UNION on partitioned tables wastes massive CPU and I/O resources.
  • Pipeline Efficiency: When writing ETL pipelines, streaming with UNION ALL enables downstream consumers to begin processing rows before the second query has finished executing.

Real-World Practical Scenario

Multi-Channel Payment Settlement Stream: Extract settled payments alongside pending customer invoices to generate a unified financial auditing stream.

Production Query: Multi-Channel Settlement Stream 
SELECT sale_id AS transaction_id, customer_id, total_price AS amount, payment_status, 'SETTLED_STREAM' AS stream_source
FROM sells_list
WHERE payment_status = 'PAID'
UNION ALL
SELECT sale_id AS transaction_id, customer_id, total_price AS amount, payment_status, 'PENDING_STREAM' AS stream_source
FROM sells_list
WHERE payment_status = 'PENDING'
ORDER BY amount DESC;

Multi-Channel Settlement Stream Breakdown

Auditing the execution logic and relational mechanics of this query:

  • Combines 46: Combines 46 matching financial transactions across two distinct payment lifecycles into a single prioritized audit stream.
  • Maintains absolute event fidelity: multiple purchases by the same customer are preserved without deduplication.
  • Sequences The: Sequences the entire combined revenue flow from highest to lowest monetary amount.

Best Practices & Production Guidelines

  • Avoid Premature Deduplication: If deduplication is needed only on a specific key, do not use UNION; use UNION ALL inside a subquery and apply DISTINCT ON or window functions (e.g., ROW_NUMBER()) for finer control.
  • Explicit Column Projection: Never project SELECT * across UNION ALL branches. Explicit column names ensure resilience against future schema changes.
  • Index Driving Columns: Ensure filter predicates (such as payment_status and product_id) are indexed so individual branch queries execute rapidly.
  • Compare with Regular UNION: Review The UNION Operator to understand when deduplication is strictly necessary.

Chapter Summary

The UNION ALL operator offers fast, streaming vertical concatenation across independent queries, preserving complete historical event frequencies without the overhead of row deduplication.

  • Duplicate Preservation: Keeps all matching records from every participating query.
  • Superior Performance: Eliminates memory-intensive sorting and hash table construction.
